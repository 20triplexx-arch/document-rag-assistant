# 第23课 多服务协作先确定数据与权限边界

模块：MCP 与协作 | 建议用时：阅读25分钟 + 动手20分钟

## 学习目标

为多工具任务定义输入输出；控制凭据传递；识别任务跨服务时的副作用。

## 中文讲解

多服务协作可以把“查到一个问题”转成“建立一个待办”，但连接更多服务也引入更多权限和失败点。先画数据流：从 GitHub 读哪项信息，生成什么摘要，向日历写什么字段。每次跨边界都要确认必要性和授权。

不同服务返回的数据不能靠自然语言想象转换。日期必须有时区，标题应有长度限制，事件创建成功应有事件 ID。某个服务失败时，需要区分已经读取的数据与尚未执行的写入，避免把整个任务重新执行一遍。

上游 Multi-MCP 案例连接多个服务，并在启动时生成用户和会话 ID。源码把整个进程环境传给子服务；这是学习时值得审视的点，因为无关凭据也可能被继承。独立实现应只传必要变量，权限范围也应按任务选择。

> 流程：只读取证 → 结构化任务草稿 → 校验字段与授权 → 必要写入 → 保存结果 ID

不要把“服务已经连接”当作“所有操作已经允许”。本课程不操作你的邮箱、日历或仓库，案例只是说明编排方法和复现条件。你自行学习时也应从只读工具和测试数据开始。

## 示例与观察

事件草稿示例：
```python
draft = {"title":"复查RAG故障记录",
         "date":"2026-10-20",
         "timezone":"Asia/Shanghai",
         "source":"教学任务"}
assert draft["timezone"]
print(draft)
```
仅创建字典，不创建真实日历事件。

## 动手任务

设计“读取问题列表并生成待办草稿”的两阶段流程，列出每阶段所需权限。

## 参考答案

第一阶段只读仓库问题，第二阶段在本机生成草稿，不需要日历写权限。真正创建事件是第三阶段，需校验字段并取得对应授权。不要为只读任务一开始就授予全面管理权限。

## 常见问题

问：共享同一套环境变量更方便吗？答：方便不意味着必要，应按服务最小需求传递变量。

问：随机 session ID 能恢复上次会话吗？答：只有重新使用旧 ID 才能定向恢复，随机生成通常意味着新会话。
