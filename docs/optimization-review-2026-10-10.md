# 项目优化检查 · 2026-10-10

结论：优先改善检索证据质量、建立固定题集，再优化检索速度和失败恢复。当前 216 篇、4220 个片段已经足够暴露问题；继续扩库之前，应能说明改动让哪些问题找到了更好的依据。

本轮阅读 README、产品约束、核心检索、接口、存储、页面脚本及既有质量复核；离线执行 6 次检索、1 次性能剖析、3 次原文/索引校验和 1 次接口替身复现。78 项后端、14 项前端测试通过。未调用真实模型，未执行课程/案例代码，未改账号库、教材快照、运行配置或功能代码。

## 1. 优先修检索证据的内容质量

入口：[概念检索](../study_rag/rag.py)、[关键词与别名](../study_rag/core.py)。

复现问题：

| 提问与范围 | 实际返回的证据 | 影响 |
| --- | --- | --- |
| “混合检索 RAG 案例如何结合关键词和向量检索？”；仅案例 | 第一个是 `Contributing`，第二个是安装/启动步骤 | 命中正确案例文件，但没有取到解释检索机制的正文 |
| “混合检索怎样提高文档问答的效果？”；仅案例 | 同样优先返回贡献说明和安装步骤 | 不是某一个特定问句的偶然现象 |
| “RAG 和长期记忆有什么区别？”；全部资料 | Agentic AI 第一条是学习目标；Microsoft 第二条是课程简介 | 提到概念不等于解释概念，不能把这些段落当作定义依据 |
| “我想让机器人记住上周聊过的内容，该怎么做？”；全部资料 | Microsoft 返回 Discord 社交邀请；其他集合有若干偏离意图的片段 | 口语问法的相关性不足，按集合取证会夹入弱证据 |
| “请解释工具调用的参数定义和错误处理代码”；仅案例 | 两条都是学习目标 | 当前概念模式过滤代码，且独立实现文件只链接，无法提供代码级讲解证据 |

混合检索案例的第一条原文在 [README 第 91～93 行](https://github.com/Shubhamsaboo/awesome-llm-apps/blob/4bf51ab704fb2c5b3803cd5191b30d7dcdb51dc2/rag_tutorials/hybrid_search_rag/README.md#L91-L93)，确为贡献邀请。后端“命中对应案例”的既有测试不能证明返回的是教学依据。

代码原因：`retrieve` 将中文章名、当前小节标题和正文拼成一个词频向量；章名中的“混合检索”“RAG”会加到同一篇的每个片段上，包括贡献说明。简短无关段落会受长度归一化影响而排在正文前面。当前只要分数非零便入选；现有过滤覆盖部分习题/资源标题，没有完整识别学习目标、贡献、社交邀请等内容。

建议：

- 把正文、小节标题、章节元数据分开计分；元数据用于定位案例，正文应满足实际内容匹配，不能仅因章名命中就成为讲解证据。
- 对概念问题过滤或降低贡献、许可证、社交邀请、学习目标的权重；对“如何安装/运行”的问题仍允许安装说明，避免全局删掉有效内容。
- 先召回候选，再依据内容类型、概念覆盖、正文匹配和重复程度排序；正文片段去重，优先补充定义、机制、限制和具体例子。
- 保留每集合最多 2 条、总计最多 8 条的上限；没有足够相关依据时留空。当前各集合的 BM25 分数使用不同统计量，不能直接当成可比较的全局分数。
- 五集合按顺序交替取证并截取 8 条，会固定丢弃最后两集合的第二条候选。若改分配规则，须在相关性、来源覆盖与用户已确认的上限之间一起评测。

验收先覆盖上表反例：概念提问不能把贡献邀请、学习目标、仅元数据命中的段落作为主要依据；安装问题仍找得到安装步骤。原文字符/行号、固定版本链接及现有模型调用上限必须保持。

## 2. 建立能衡量改进的固定题集

现有 92 项测试主要证明来源完整性、交互、账号隔离、预算和引文出处；不证明检索足够相关或引文支持结论。[早期真实试答](../reviews/2026-10-09-deepseek-pilot.md)仍未通过内容质量验收。

建议先人工标注约 30～40 题，覆盖四课程与案例、单集合/跨集合、中英术语/口语改写、资料不足和本轮反例。开发题与保留题分开；每题记录可支持结论的段落和无关反例，不只标“来自哪篇文档”。

先离线统计前 8 条是否包含支持性段落、无关证据比例和必要概念覆盖；再在用户确认预算后做真实生成评测，分别记录引文出处、逐条结论支持和资料不足时的回答。不要为了通过题集把题目答案写入检索别名。所有改进门槛应在看到保留题结果之前确定，本轮没有建立完整题集或宣布质量验收。

## 3. 缓存固定快照的检索准备工作

入口：[verified_chunks](../study_rag/core.py)、[retrieve](../study_rag/rag.py)、[/api/library 与 /api/ask](../study_rag/web.py)。

本机非性能剖析的观察值：

| 检查 | 耗时 |
| --- | --- |
| 全部资料的 RAG/记忆问题 | 1.2841 秒 |
| 全部资料的口语记忆问题 | 1.2938 秒 |
| 案例单集合的四次提问 | 0.5173～0.5539 秒 |
| 单次整套原文/索引核对，3 次 | 0.2965～0.3322 秒 |

这些是当前机器上的少量样本，既不包含模型耗时，也不代表 p95、并发能力或正式基准。追加查询/校验期间测试进程也在运行，不能据此做精确性能比较。

一次全范围检索的剖析显示：重新加载整套原文 2 次、重新分块 216 篇、正文遮罩 216 次、分词 3404 次。`index.sqlite3` 目前持久化的是片段 JSON，每次查询仍完整读回并重新计算原文片段进行比较；不是已经持久化的词项倒排索引。指定资料范围时，接口还会额外调用一次 `verified_chunks` 验证集合 ID。

建议先让服务在载入一个固定快照时完成全量核对，并建立不可变的正文遮罩、词频、文档频率、集合目录及按词项查候选的数据。以语料版本、索引契约和检索器版本区分缓存；切换或检测到文件变化时使缓存失效并重新核对，失败就拒绝使用。明确服务使用已载入的固定快照，不允许缓存静默接受损坏的数据或绕过引用回查。

首轮保持现有依赖和 SQLite；使用相同题集与原文检查，对比冷启动、热查询、峰值内存和排名一致性。暂不承诺某个毫秒目标。若后续扩库确需持久倒排索引，可评估 [SQLite FTS5](https://www.sqlite.org/fts5.html)，它支持全文查询和 BM25；中文分词、别名、字段权重及原文映射仍需专门验证，不能直接换默认分词器就宣布效果变好。

## 4. 修失败恢复与输入错误提示

入口：[提问提交](../static/app.js)、[请求复用](../study_rag/web.py)。

前端每次点击提交都生成新的 `request_key`。根据代码推断：如果服务端已保存答案，但响应在网络中丢失，用户重试会携带新编号，现有后端去重无法识别为同一请求，可能再次生成并计入额度。本轮没有在真实服务制造该故障或实际重复调用模型。

建议同一问题、范围、模式与讨论在收到明确结果之前复用请求编号；网络失败后先查询该请求的状态/已有结果，改变问题或明确开始新请求才换编号。请求完成后的历史刷新失败也应与生成失败区分，避免已展示答案又被提示“提问失败”。所有恢复逻辑继续校验账号和讨论所有权，不共享私人结果。

另用无数据库、无模型调用的替身复现：提交“如何”这种没有具体概念的提问，当前返回 503“教材或索引核对失败”。原因是用户输入问题与真正的原文损坏共用 `CorpusError`。应将输入语义校验分为 422，提示提供具体概念；只有原文/索引损坏才返回 503。加入对应接口与前端恢复测试。

## 5. 把案例浏览变成完整学习流程

当前 12 个案例 README 已索引，17 个独立实现文件仅提供 GitHub 链接；网页“只查原文”仍使用过滤代码的概念检索，CLI `search` 才能检索 README 内代码。代码级提问因此不能简单沿用概念模式。

后续可在现有目录上增加本地正文阅读、选中案例后提问和对应章节入口；分别支持概念解释、运行步骤、代码阅读，检索时按意图选择内容。若纳入独立实现文件，必须另建固定版本快照，保留原文/行号和许可核对；继续只阅读，不执行案例或安装框架。

追问也属于独立产品改进：当前 Prompt 只有本次问题和证据，“那它和另一种有什么不同”不会自动带上本讨论的前文。若加入追问上下文，只允许当前账号、当前讨论的有限上下文，不能把其他用户记录放进共享检索或 Prompt；仍保留单题一次模型调用限制。本轮不改变目前每题独立检索的既定行为。

## 6. 语义检索放在可对照评测之后

口语中文检索英文案例时，有限术语别名无法覆盖所有表达。建议在上述基线可测之后，再评估本地多语言向量召回与关键词召回融合，必要时加重排。

融合算法可参考 [Microsoft 的 RRF 排序说明](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)：它按多个召回列表中的名次融合，避免直接相加不同尺度的分数。这是算法参考，不是让本项目迁往 Azure。嵌入模型、许可、运行资源和效果还需单独检查，本轮没有下载模型、接入向量服务或验证语义检索效果。

## 推进顺序与证据

第一批：标注固定检索题，修正文/标题计分和内容类型筛选，增加本轮失败样例的回归检查；随后缓存已核对快照，检查排名、来源核对和性能。第二批：请求编号复用、错误分类和失败恢复。第三批：案例阅读/代码检索、有限追问上下文、语义检索对照实验。每批单独记录验收，保护旧快照和账号库。

原始离线检索/剖析数据保存于忽略提交的 `output/optimization-audit-2026-10-10.json`，只含公开资料片段、测试问题与计时；不含私人讨论、凭证或账号信息。本轮没有修改功能代码或切换配置，以上建议均待实施和验证。
