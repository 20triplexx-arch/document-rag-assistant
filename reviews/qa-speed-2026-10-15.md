## SPEED-A2

用户隔天开了新 thread，希望保留饮食偏好，但不自动带回上次聊天。thread、namespace/key 和后台写入记忆各负责什么？

thread/namespace 主体有依据；引用只说明可后台更新，并未覆盖具体延迟取舍，回答却补充不阻塞与延迟；把读取时机限定在新 thread 初始化也过窄。

检索标注支持覆盖：3/4；该数不是内容正确率。

thread 是会话内的短期记忆边界，只承载该会话的对话历史，新 thread 不会自动读取旧 thread 的消息；饮食偏好属于跨会话的长期记忆，存在 store 里的 namespace/key 下，由应用在新 thread 中主动检索，因此“保留偏好但不自动带回上次聊天”正是把偏好放长期、把聊天记录留短期的结果。

thread 负责把多次交互组织成一个会话：短期记忆是 thread 作用域的，以消息历史形式维护当前对话，并由 checkpointer 持久化，使该 thread 可随时恢复，更新发生在图被调用或某一步完成时、每步开始时读取。因此换到新 thread 后，上一轮的消息历史不进入上下文，不会被自动带回来。

长期记忆跨 thread 和会话存在，可随时、在任何 thread 中被召回，作用域是自定义 namespace 而非单个 thread ID。LangGraph 把长期记忆存成 store 里的 JSON 文档；namespace 类似文件夹，常包含用户 ID 或组织 ID 等标签，key 类似文件名，用于在该 namespace 下区分每条记忆，这种结构支持分层组织和跨 namespace 的内容过滤搜索。像“用户对某类食物过敏”这类事实属于语义记忆，适合记为长期记忆。

后台写入记忆解决的是“什么时候把偏好写进长期 store”：记忆既可以作为应用逻辑在热路径上更新（通常在回复用户前由 agent 决定记住哪些事实），也可以在后台异步生成记忆。后台方式不阻塞当次对话，但写入有延迟；要覆盖“隔天新 thread 仍保留偏好”，还需在新 thread 初始化时从 store 按 namespace/key 把偏好检索进上下文，否则它只是存在 store 里而未被使用。

perform_search 是独立的“混合检索→取块→重排”函数，只返回重排后的片段列表；而 rag 是另一次调用，传入的是 search=hybrid_search（不是 perform_search，也不是重排结果）。因此回答不会复用刚才那批重排片段：perform_search 的结果只被用来判断是否为空，非空时对 rag 的调用会重新执行一遍 hybrid_search 的检索流程（重排也只发生在 perform_search 内部）。

另外，fallback 分支在 reranked_chunks 为空时直接调用 Claude 用通用知识回答，连检索都不再做；只有非空时才走 rag。

EVIDENCE 只提供了调用方 main.py 的片段，没有 raglite 内部 rag(search=...) 与 hybrid_search 的实现，因此无法从源码确认 rag 内部是否会对 hybrid_search 结果再做重排或其它处理；只能确认调用层没有把 perform_search 的重排结果传给 rag。

内部状态：write_todos 维护的结构化任务清单（状态 pending/in_progress/completed），持久化在 agent state 中，是轻量规划层，用于组织长任务和给前端流式展示进度。

## SPEED-A5

工具通过 runtime 得到用户身份，聊天历史又越来越长。应该把身份作为模型生成的参数吗？model context 与 tool context 有何区别，trim 和 delete 分别改变什么？

身份由 runtime 注入而非模型填写、模型输入与工具上下文的区分、trim 与 delete 的影响均能定位本轮资料；摘要部分偏长，可继续精简。

检索标注支持覆盖：3/4；该数不是内容正确率。

不应该把身份作为模型生成的参数。工具本来就能通过 ToolRuntime 拿到运行时信息，包括调用时传入、不可变的 Context（用户 ID、会话信息），正好用于按用户身份个性化响应；而且以 state 为例，runtime 参数由 ToolNode 在调用时自动注入，不会出现在发给模型的工具 schema 里，模型看不到它。把身份放进模型生成的参数，等于要求模型自己填对，既多此一举又失去了运行时注入的可靠性。

model context 和 tool context 的区别在于“谁看到”和“是否持久”。model context 是单次模型调用里放进去的东西（指令、消息历史、工具定义、响应格式），属于 transient：可以改消息、工具或提示而不改动 state 里保存的内容；tool context 是工具能读能写的东西（对 state、store、runtime context 的读写），属于 persistent：工具写入会永久修改保存的状态。生命周期上下文（摘要、护栏、日志）同样属于 persistent，作用于模型调用与工具调用之间。

trim 和 delete 改变的对象不同。trim 只影响单次模型调用看到的上下文，不改变 state：做法是统计消息历史的 token 数，接近上限时按策略截断，例如保留最后 maxTokens 个 token。delete 则直接移除指定消息，会改变保存的历史，因此必须保证删完后历史仍然合法——有些提供方要求历史以 user 消息开头，多数提供方要求带工具调用的 assistant 消息后面跟着对应的 tool 结果消息。如果希望长期压缩而不是每次调用临时截断，可以用 SummarizationMiddleware：它用一次单独的 LLM 调用摘要较早的消息，把摘要消息永久写回 State 替换原文，同时保留近期消息。

## SPEED-A7

退款专员需要直接接待用户，后台检索员只需交回核查报告。这两项分别适合 handoffs 还是 subagents？总控是否自动看到后台检索员的完整聊天历史？

选择 handoffs/subagents 的方向正确；把 Deep Agents 特有的 isolated/fork 配置当作未限定框架的通用 subagents 行为，且重复结论。

检索标注支持覆盖：0/4；该数不是内容正确率。

退款专员直接接待用户，适合 handoffs；后台检索员只交回核查报告，适合 subagents。

依据是各模式在“直接用户交互”上的适配度：handoffs 被评为五星，subagents 只有一星。而 subagents 的定位就是主 Agent 通过工具调用的下属，其特点是不直接与用户交互，结果只返回主 Agent；它由主 Agent 统一路由，可并行执行，各自在隔离上下文中运行，最后只交回一份报告。所以需要面对用户的退款专员用 handoffs，只需交报告的后台检索员用 subagents。

总控不会自动看到后台检索员的完整聊天历史。subagents 默认以隔离模式运行（mode: "isolated"），每次调用新建带自己上下文的 Agent 实例，只向主 Agent 返回一份最终报告，且是无状态的、不能回传多条消息。要让它继承父级完整对话历史需显式使用 mode: "fork"，这属于可选配置而非默认行为。

## SPEED-A8

同一讨论连续问两次，第二次经历模型、工具、模型三个步骤。LangSmith 应如何组织 run、trace 和 thread？HTTP 200 能证明答案正确吗，还需要什么评估？

两轮 trace、三个 run、同一 thread 与独立正确性评估均有本轮依据；说明仍偏长，有可删的重复与额外工具举例。

检索标注支持覆盖：4/5；该数不是内容正确率。

第二次问的这次执行整体构成一个 trace：模型调用、工具调用、再模型调用三次 run 都通过同一个 trace ID 绑在这个 trace 下；第一问那次构成另一个 trace，两次 trace 用相同的 thread_id 元数据键归入同一个 thread。HTTP 200 只能说明请求被成功接收，不能证明答案正确，正确性要靠准确性等评估指标判断。

run：单个工作单元，如一次 LLM 调用、一次提示格式化或一次文档检索；可类比 OpenTelemetry 的 span。第二次问的模型→工具→模型就是三个 run。

trace：一次操作的全部 run 集合，run 通过唯一 trace ID 绑定到 trace；用户请求触发 agent 调模型、跑工具、再调模型，这些 run 属于同一 trace。

thread：代表单次多轮会话的 trace 序列，一个 turn（用户一条消息加上 agent 的全部响应）记录为自己的 trace；group 方式是对关联 trace 传同一个 thread_id 元数据键。第一次和第二次问各是一个 trace，共享 thread_id 后归入同一 thread。

按用途选择查看对象：调试单次操作为何失败或慢看 trace，跨轮查看 agent 行为（保留时序与嵌套）看 thread，只看会话交换内容而不看执行细节则看 trajectory（扁平、有序、去重后的消息列表）。

HTTP 200 不是正确性的证据，它只表明请求成功与否这一层。评估答案正确性需要看准确性：为 agent 定义成功标准，通过自动化检查、评估分数或任务完成标签追踪，例如把 trace 标记为成功或失败；也可以用自动化评估，如用 LLM 给输出打分判断是否有用、准确，或对 RAG agent 用 RAGAS、检测有害语言或提示注入用 LLM Guard。可观测性层面还常配合延迟、成本、请求错误、用户反馈和隐式反馈等指标，但它们衡量的是运行健康与体验，不替代正确性判断。
